## 0. 开发前必须阅读的说明

本文件不是一个只画页面的 UI 设计稿，而是针对现有后端交易能力制定的**真实交易前端需求与接口集成规范**。

必须遵守以下原则：

1. **真实 API 优先**：所有账户、行情、持仓、委托、撤单、下单和快捷交易数据，必须来自现有后端 API。禁止 mock、假数据、静态模拟持仓、模拟成交、伪造委托结果或用前端计算结果冒充券商返回结果。
2. **功能完整**：`OptionTradeController` 当前已经开放的全部 15 个有效路由必须在页面中有对应入口、交互和结果反馈。任何功能不得因为 UI 复杂、开发方便或个人主观判断而被删除、隐藏或降级。
3. **尊重后端真实行为**：不得只根据接口名称猜业务语义。必须以 Controller、Service、ServiceImpl、DTO、Enum 和底层 API 的实际代码为准。
4. **不伪造成功**：HTTP 请求返回成功不等于委托成交；委托受理不等于全部成交；快捷批量操作返回 `Void` 不等于每一笔都成功。必须在提交后刷新委托、持仓并展示真实状态。
5. **不暴露交易凭据**：浏览器只调用本项目的 `/api/option/trade/**`，绝不能直接请求东方财富交易站点，不能在 HTML/JS 中写入 `SID`、Cookie、`validatekey`、账号、密码或其他会话凭据。
6. **交易确认必须明确**：撤单、下单、清仓、减仓、分档下单等改变真实账户状态的操作，必须由用户主动点击触发，并在执行前展示清晰的操作确认信息。
7. **发现后端缺陷不得绕开**：已确认的后端逻辑风险必须登记为阻断项。不得在前端“猜一个算法”绕过后端，也不得把存在缺陷的接口包装成可靠功能。应保留功能入口与接口映射，同时在问题修复前禁用相应危险操作或展示明确阻断提示。

# 第二部分：产品需求文档（PRD）

## 2. 项目概述

### 2.1 项目背景

现有 `tdx-quant` 后端已经封装了 A 股 ETF 期权账户资金、持仓、合约检索、实时五档行情、最大可交易数量、手动下单、当日/历史委托、可撤委托、批量撤单及多种快捷交易操作。

本项目目标是在不重复实现交易业务、不把券商接口搬到浏览器、不改变现有量化系统主体结构的前提下，为这些后端能力提供一套统一、直观、低操作成本的原生 HTML 交易工作台。

页面不是行情展示 Demo，而是现有真实交易 API 的完整交互入口。

### 2.2 产品定位

| 项目 | 定义 |
|---|---|
| 产品名称 | tdx-quant ETF 期权交易工作台 |
| 市场 | 中国大陆沪深交易所 ETF 期权 |
| 交易通道 | 现有 `tdx-quant` Spring Boot 后端 |
| 交易 API | `OptionTradeController` |
| 行情来源 | 现有后端封装的东方财富沪深行情快照 API |
| 交易执行 | 现有后端封装的东方财富 ETF 期权交易 API |
| 前端技术 | 原生 HTML5 + CSS + JavaScript |
| 文件规模 | 优先单 HTML 文件，最多 3 个文件 |
| 部署方式 | Spring Boot `classpath:/static/` |
| 页面职责 | 真实账户展示、真实交易指令提交、结果核对 |

### 2.3 核心目标

- 将当前 Controller 已开放的所有交易能力全部映射成可操作 UI。
- 让用户在一个页面内完成账户检查、合约选择、行情查看、下单、持仓管理、撤单和快捷交易。
- 真实 API 响应作为唯一事实来源。
- 降低误操作、重复提交、错误合约、错误数量、陈旧行情和未核实成交造成的风险。
- 不引入复杂前端工程化体系，保持单文件、可读、易维护。

### 2.4 非目标

以下内容不属于本页面第一期功能，不得为填充页面而虚构：

- 新建或替换券商登录系统。
- 在浏览器中直接请求东方财富交易 API。
- 在浏览器中存储券商 Cookie、SID、validatekey。

## 4. 用户角色、权限与使用前提

### 4.1 用户角色

- **交易操作用户**：查看账户、持仓、委托，提交真实交易指令。
- **系统维护者**：维护后端交易会话、服务部署、API 权限和日志。

### 4.2 前置条件

- Spring Boot 服务正常运行，默认服务端口配置为 `7001`。
- 后端已经正确装载券商会话和交易请求所需的服务端配置。
- 后端调用东方财富交易 API 的网络连接正常。
- 账户已经依法取得 ETF 期权交易资格，并具有对应交易权限。
- 用户通过既有后端和券商认证机制获得合法授权。

### 4.3 前端权限原则

前端只负责展示和提交指令，不能自行认定账户具备交易权限。账户权限、期权适当性、交易所限制、最大可交易数量和真实可用数量必须以券商/后端响应为准。

页面不能提供绕过身份核验、年龄要求、账户权限、适当性要求或监管限制的入口。

7. 展示二次确认窗口：ETF、合约、买卖开平、报价方式、价格、数量、当前行情时间、最大可交易数量。
8. 用户确认后调用 `bs`。
9. 立即禁用提交按钮，避免重复点击。
10. 若响应成功，显示返回的委托编号，并刷新当日委托。
11. 若请求超时或网络中断，不得自动重发；状态显示“结果待核实”，主动刷新当日委托核对是否已经生成委托。
12. 委托是否成交，以订单状态、成交数量和成交金额为准，而不是以 `bs` 返回委托号为准。

### 6.5.6 价格与数量原则

- 不得将普通股票的 2 位价格精度、ETF 的 3 位价格精度直接套到期权。
- 后端期权快捷卖出、等比减仓和快捷买入代码中使用 4 位价格精度；前端默认按 4 位精度呈现，并以最终交易 API 校验为准。
- 数量只接受正整数。
- 不允许直接套用股票 100 股一手的数量逻辑。
- 不凭空计算手续费、保证金或理论最大开仓量；只有后端响应提供的字段才可以作为确定数据展示。

## 6.10 一键清仓

**对应 API**：

```http
GET /api/option/trade/quick/clearPosition
```

### 6.10.1 当前后端真实流程

当前 `OptionTradeServiceImpl.quickClearPosition()`：

1. 调用 `quickCancelOrder()`。
2. `quickCancelOrder()` 查询当日全部委托。
3. 过滤后批量撤销全部未成交委托。
4. 等待约 1 秒。
5. 重新查询账户资金和期权持仓。
6. 对持仓列表调用内部 `quick__clearPosition()`。
7. 内部再走 `quick__sellPosition()`，逐笔提交卖出平仓委托。

**重要：当前代码撤销的是全部未成交委托，不是仅撤销未成交卖单。** 页面文案必须准确说明这一点。

### 6.10.2 页面要求

- 页面明显显示当前持仓合约数、当前可用合约总数、未成交委托数。
- 点击“一键清仓”后先弹出强确认对话框。
- 确认框必须说明：将先尝试撤销当前全部未成交委托，再重新读取持仓，随后按后端逻辑提交清仓委托。
- 确认框不得将此操作描述成“立即全部成交”或“保证清仓”。
- 可要求用户再次输入确认词，例如 `CLEAR`，作为前端防误触措施；不得把该确认词当成后端身份认证或交易授权。
- 执行期间全局交易按钮禁用。
- 接口返回后重新获取账户资金、持仓、当日委托、可撤列表。
- 展示清仓后真实剩余持仓与未成交卖单。若仍有持仓，显示“清仓未完成/仍有剩余持仓”，不得显示“清仓成功”。

### 6.10.3 已知阻断问题

内部清仓方法无论持仓方向如何，当前都设置为 `SELL_CLOSE`。持仓 DTO 同时包含 `Ccfx`（权利仓/义务仓），因此对于义务仓，必须确认应使用的平仓方向并修复后端。修复前不能将一键清仓作为对所有持仓方向都可靠的能力。

## 6.11 指定合约一键等比卖出

**对应 API**：

```http
GET /api/option/trade/quick/sellPosition
    ?sellStockCodeList={Hybm1,Hybm2}
    &sellPosPct={卖出百分比}
    &currPricePct={当前价偏移百分比}
    &prevPricePct={昨收价偏移百分比}
```

### 6.11.1 参数

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---:|---|
| `sellStockCodeList` | String | 必填 | 逗号分隔的期权合约编码 Hybm |
| `sellPosPct` | double | 100.0 | 卖出持仓比例，百分数口径；100 表示按后端逻辑卖出全部可用数量 |
| `currPricePct` | double | 0.0 | 当前价涨跌幅比例；0 表示使用实时价 |
| `prevPricePct` | double | 0.0 | 昨收价涨跌幅比例；0 表示不启用昨收价方式 |

### 6.11.2 当前后端价格与数量逻辑

- 当前价模式：实时当前价 ×（1 + `currPricePct` / 100）。
- 昨收价模式：昨日收盘价 ×（1 + `prevPricePct` / 100）。
- 若 `prevPricePct != 0`，后端优先使用昨收价模式。
- 计算出的卖出价格再乘以 `0.995`，以 4 位小数 HALF_UP 处理。
- 卖出数量按可用数量 `Hysjcc` × `sellPosPct` / 100 取整数，并限制不超过可用数量。
- 当前代码固定使用 `SELL_CLOSE` + `LMT`。

### 6.11.3 页面要求

- 仅可选择当前持仓列表中的合约。
- `sellStockCodeList` 必须传 `Hybm`，绝不是 `bdzqdm`（标的 ETF 代码）。
- 选中合约后展示每个合约的当前持仓数和可用数量。
- 卖出比例输入范围限制为 0～100；数量预览应明确标注为估算值。
- 当前价偏移和昨收价偏移只能选择一种模式；不能让两个偏移同时生效。
- 预览必须标记后端会将价格再乘以 `0.995`，并说明这是当前 Service 实现逻辑。
- 执行前确认合约列表、每只合约的可用数量、卖出比例和价格模式。
- 执行后刷新持仓和委托，以实际结果核对。
- 如果计算出卖出数量为 0，不应发送无意义订单；但“是否为 0”必须基于后端数量规则/校验结果，不得伪造已经卖出。

### 6.11.4 已知限制

当前后端固定 `SELL_CLOSE`，未依据 `Ccfx` 区分义务仓。该接口的真实适用范围必须在修复并完成方向测试后确定。

## 6.12 账户总仓位一键等比减仓

**对应 API**：

```http
GET /api/option/trade/quick/totalAccount/eqRatio/sellPosition?newPositionRate={0到1之间的小数}
```

### 6.12.1 参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `newPositionRate` | double | 新的账户目标总仓位比例，后端使用 0～1 小数口径 |

页面可以用百分比输入，例如输入 40%，请求参数必须转换为 `0.4`，不能把 `40` 直接传给后端。

### 6.12.2 设计要求

- 显示当前账户总仓位比例。
- 输入目标仓位比例。
- 展示当前值、目标值、预计需要减仓的比例差值。

- 操作后刷新账户和持仓，展示真实新仓位。

### 6.12.3 P0 后端阻断缺陷

当前 `check___totalAccount__equalRatioSellPosition()` 的条件存在明显逻辑矛盾：

- 第一条断言要求 `actTotalPosRatio < newPositionRate`；
- 后续又要求 `actTotalPosRatio - newPositionRate > 0.05`。

这两个条件对于正常数值不可能同时成立。该接口按当前代码不能作为可用的账户总仓位减仓功能。

**需求处理：** UI 与 API 映射必须保留；但在后端修复并通过单元测试、集成测试前，执行按钮必须显示阻断状态，不能发出真实请求。后端修正后，前端再解除阻断。

### 6.12.4 后端修复验收建议

- 当前总仓位大于目标仓位超过 5 个百分点：允许进入减仓流程。
- 当前总仓位小于或等于目标仓位：不应发出卖出指令，应返回明确提示。
- 当前总仓位与目标仓位差值不超过后端阈值：按后端业务规则返回明确拒绝原因。
- 目标仓位边界值、0、接近 1、负数、大于 1 均应测试。
- 修复后必须验证不同持仓数量、不同可用数量、权利仓/义务仓混合持仓。

## 6.13 当前持仓一键等比减仓

**对应 API**：

```http
GET /api/option/trade/quick/currPos/eqRatio/sellPosition?newPositionRate={0到1之间的小数}
```

### 6.13.1 参数定义

`newPositionRate` 表示：以当前持仓市值为 100% 基准，减仓后保留的仓位比例。

例如：

- `1.0`：保留当前仓位 100%，实际卖出比例为 0；但当前实现断言要求小于 1，因此不能传 1。
- `0.5`：理论上保留当前持仓市值 50%，卖出比例为 50%。
- `0.2`：理论上保留当前持仓市值 20%，卖出比例为 80%。
- `0`：理论上清空当前持仓；需以后端修正后的参数边界与可用数量规则为准。

### 6.13.2 页面要求

- 以百分比形式输入，提交前转换为 0～1 小数。
- 展示当前持仓市值作为 100% 基准。
- 显示目标保留比例和理论卖出比例。
- 执行前展示当前持仓明细和可用数量。
- 只允许明确确认后触发。
- 执行后刷新账户资金、持仓和委托。

### 6.13.3 后端风险

该接口进入 `equalRatio_sellPosition()`，其中通过 `StockUtil.quantity(qty, stkavl)` 取整。`StockUtil.quantity` 的实现是 A 股股票数量取整逻辑，存在以 100 为单位取整的行为；用于期权合约数量可能产生与用户设置的比例不一致的卖出结果，甚至在小于 100 张的持仓上造成明显偏差。

此外，等比减仓内部固定使用 `SELL_CLOSE`，没有按持仓 `Ccfx` 选择平仓方向。以上问题修复前，该功能不得作为无条件可用的真实交易按钮。

## 6.15 快捷分档下单

**对应 API**：

```http
GET /api/option/trade/quick/quickOption
    ?stockCode={标的ETF代码}
    &hybm={期权合约编码}
    &priceRangePct={价格间隔百分比}
    &rangeTotal={总档数}
    &amount={每档金额}
    &optionTradeTypeEnum={交易类型枚举}
```

### 6.15.1 参数

| 参数 | 类型 | 说明 |
|---|---|---|
| `stockCode` | String | 标的 ETF 代码 |
| `hybm` | String | 期权合约编码 |
| `priceRangePct` | double | 价格间隔百分比 |
| `rangeTotal` | int | 总档数 |
| `amount` | double | 每档金额，不是总金额 |
| `optionTradeTypeEnum` | Enum | `BUY_OPEN`、`SELL_CLOSE`、`SELL_OPEN`、`BUY_CLOSE` |

### 6.15.2 当前后端真实执行逻辑

- 先获取期权行情快照。
- 读取 `fivequote.buy1` 作为起始价格。
- 价格精度按 4 位小数处理。
- 若交易类型为 `SELL_CLOSE`，使用正向价格阶梯。
- 其他三种交易类型使用反向价格阶梯。
- 每档价格按 `priceRangePct` 逐档递推。
- 每档数量按 `amount / price` 计算整数，再通过 `StockUtil.quantity(qty, stockName)` 处理。
- 每档使用 `LMT` 报价方式调用 `bs()`。
- 档间随机等待约 500ms。
- 方法返回 `Void`，不返回逐档委托号或逐档错误明细。

### 6.15.3 页面要求

- 选择标的 ETF。
- 选择合约。
- 选择交易类型（4 种完整枚举）。
- 输入价格间隔百分比。
- 输入档数。
- 输入每档金额。
- 显示当前买一、卖一和最新价。
- 根据源码行为构造“计划档位预览”，但必须标记为前端预览，不得冒充后端最终委托价格/数量。
- 显示预计档位数、价格方向和每档金额。
- 提交前明确提示该接口将逐档连续提交多个真实委托。
- 用户确认后调用后端快捷下单接口。
- 请求完成后刷新当日委托，展示实际生成的委托单。
- 若接口超时，不得自动重发整组分档请求；必须先刷新委托列表核对，以免产生重复委托。

### 6.15.4 P0 数量口径风险

当前 `quickOption()` 把数量交给 `StockUtil.quantity(qty, stockName)`。而 `StockUtil.quantity` 是股票数量规则，包含最小数量和 100 单位取整。期权合约数量的单位和规则不能默认等同于股票股数。

同时当前 `quickOption()` 的金额换算代码没有在该方法中显式乘入或处理合约单位。源码中的持仓 DTO 有 `hydw` 合约单位字段，但分档下单方法没有在这里显式使用。必须由后端结合真实期权合约规则核验金额、合约单位和张数换算。

修复前，不允许页面将前端预估数量描述为准确数量，也不应在未经核验的情况下把该功能标记为生产可用。

## 7. API 集成规范

### 7.1 API Base URL

默认：

```javascript
const API_BASE = '/api/option/trade';
```

推荐将页面部署在与 Spring Boot API 相同的 Origin 下，避免跨域和凭据问题。

### 7.2 统一响应结构

项目 `Result<T>` 主要字段：

```json
{
  "data": {},
  "success": true,
  "code": 0,
  "msg": "成功",
  "totalNum": 0,
  "pageIndex": 0,
  "pageSize": 0,
  "totalPage": 0
}
```

数组响应时 `data` 为数组；对象响应时 `data` 为对象；无返回体业务数据时 `data` 可能为 `null`。

### 7.3 统一请求封装

原生 JavaScript 建议抽象：

- `apiGet(path, params, options)`
- `apiPost(path, body, options)`
- `unwrapResult(response)`
- `showApiError(error)`

统一处理：

1. URL 参数编码使用 `URLSearchParams`。
2. POST 使用 `Content-Type: application/json`。
3. 每次响应检查 `response.ok`。
4. JSON 响应检查 `success === true`。
5. 业务错误优先显示后端 `msg`。
6. HTTP 500 但响应体为 `Result.ERR` 时仍应读取并展示 JSON 业务错误。
7. 超时、断网、JSON 解析失败、后端非 JSON 响应分别提示。
8. 真实交易请求不得自动重试。
9. 读请求可以提供手动重试。
10. 有副作用的 GET 请求必须通过专用函数执行，只允许从明确用户点击事件触发。

### 7.4 副作用 GET 风险控制

当前 Controller 将如下真实交易操作定义为 GET：

- `quick/clearPosition`
- `quick/sellPosition`
- `quick/totalAccount/eqRatio/sellPosition`
- `quick/currPos/eqRatio/sellPosition`
- `quick/cancelOrder`
- `quick/quickOption`

前端必须：

- 不使用 `<a href>` 作为操作按钮。
- 不把这些 URL 写入图片、iframe、预加载、自动刷新资源。
- 页面初始化不得调用这些接口。
- 不使用轮询调用这些接口。
- `fetch` 调用时设置 `cache: 'no-store'`。
- 操作前展示确认框。
- 操作中禁用按钮。
- 网络异常时标记结果待确认，不自动重复提交。

**后端企业级整改建议**：为所有有副作用的路由新增 POST 版本，旧 GET 路由按兼容周期保留或明确下线；增加 CSRF/Origin 校验、幂等键、用户操作审计、请求流水号和逐笔结果返回。

### 7.5 会话与凭据

现有交易 API 依赖服务端的 `EastMoneyTradeAPI` 会话配置和请求头。前端不得感知、复制或保存这些值。

页面只允许请求本项目后端；禁止：

- 浏览器直连 `jywg.18.cn`。
- 浏览器直连 `emhsmarketwgmix.eastmoneysec.com`。
- 在 JS 中写 Cookie/SID/validatekey。
- 在 localStorage/sessionStorage 存储券商凭据。
- 在日志、错误提示或 Console 输出完整请求头。

## 8. 交易业务安全与状态机

### 8.1 下单状态必须区分

页面至少区分：

1. **未提交**：用户还没有确认。
2. **提交中**：请求正在发送。
3. **接口已受理/返回委托编号**：后端返回了委托编号，但不代表成交。
4. **委托已报/待报/未报**：按真实委托状态显示。
5. **部分成交**：显示已成交与剩余数量。
6. **已成**：真实委托状态为已成。
7. **已撤/部撤/废单**：真实终态。
8. **结果待核实**：请求超时或连接中断，不能确认是否已提交成功。
9. **快捷操作部分完成**：动作接口返回但刷新后发现部分委托失败或仍有持仓。

### 8.2 撤单状态

以下为当前源码中的状态分类：

- 未成交类：待报、未报、已报、部成。
- 已结束类：已撤、部撤、已成、废单。

前端必须保留后端原始状态文字，状态颜色只是视觉辅助，不能替代状态值。

### 8.3 防重复操作

- 单笔下单按钮点击后立即进入 loading 状态。
- 同一张委托不能重复发出批量撤单请求。
- 全局快捷操作互斥：清仓、等比卖出、总仓位调整、分档下单不能并发执行。
- 页面刷新或重新打开时，不得自动恢复并重放上一次交易请求。
- 接口超时不允许自动重试真实交易请求。
- 用户第二次提交前，应刷新当日委托或明确确认上一笔状态。

### 8.4 二次确认标准

| 操作 | 确认强度 | 必须展示 |
|---|---|---|
| 手动单笔下单 | 普通二次确认 | ETF、合约、交易类型、报价方式、价格、数量 |
| 批量撤单 | 二次确认 | 笔数、委托号、交易所、状态 |
| 一键撤单 | 强确认 | 全部未成交委托数量及买卖方向范围 |
| 指定合约等比卖出 | 强确认 | 合约列表、可用数量、比例、定价模式 |
| 当前持仓等比减仓 | 强确认 | 当前总持仓基准、目标保留比例、理论卖出比例 |
| 账户总仓位等比减仓 | 强确认 | 当前账户仓位、目标仓位、差值、后端校验状态 |
| 一键清仓 | 最高级确认 | 全部未成交委托可能被撤、所有持仓将进入清仓流程 |
| 分档快捷下单 | 强确认 | 档数、每档金额、价格间隔、交易类型、价格方向 |

### 9.1 关键源码风险解释

#### A. 账户总仓位断言

当前先断言“当前总仓位小于新目标仓位”，后续又要求“当前总仓位 - 新目标仓位大于 5%”。同一组数值不可能同时满足。因此 UI 不得为了满足“功能按钮要可点”而绕过后端校验。

#### B. 期权数量与股票数量单位混用

`StockUtil.quantity` 注释明确围绕 A 股股票数量、100 股一手和科创板最小 200 股起买展开。期权持仓数量和股票股数不是同一单位。复用这类方法时必须先确认真实期权委托单位，否则不能把取整结果当成合法张数。

#### C. 权利仓和义务仓

持仓 DTO 提供 `Ccfx`（权利仓/义务仓），交易类型枚举同时支持 `SELL_CLOSE` 与 `BUY_CLOSE`。清仓和等比减仓代码固定使用 `SELL_CLOSE`，没有根据持仓方向选择平仓类型。因此在权利仓/义务仓混合持仓的真实账户上，不能直接把该实现认定为“无条件清空全部头寸”。

#### D. Void 快捷操作

一键清仓、快捷卖出、等比减仓、分档下单等路由返回 `Result<Void>`。这类返回只能说明调用链没有向 Controller 抛出最终异常，不包含完整逐笔成交或逐笔失败明细。页面必须刷新委托与持仓做二次核对。

## 10. 非功能性需求

### 10.1 性能

- 首屏只发起必要只读请求。
- 账户资金和持仓请求可合并为一次 API 调用。
- 委托列表、可撤列表避免无必要的重复并发刷新。
- 行情轮询可配置，默认 2～3 秒，并在页面不可见时暂停。
- 对交易 API 不并发轰炸；前端操作互斥，后端已有交易限流时仍需遵守。
- 大量历史委托应采用表格分页/虚拟滚动的轻量实现；当前后端返回列表时，前端不得假装具备服务端分页。

### 10.2 兼容性

- 现代桌面 Chrome、Edge、Safari。
- 使用原生 Fetch、URLSearchParams、AbortController、Dialog 等现代浏览器能力。
- 页面部署在当前 Spring Boot 静态资源目录内。
- 不依赖 Node.js 构建、不依赖 npm、不需要前端打包。

### 10.3 安全

- 不暴露交易凭据。
- 不将敏感账户字段写入 Console。
- 动态数据采用 `textContent` 或安全 DOM API 渲染。
- 不把后端错误堆栈直接作为 HTML 插入页面。
- 不将交易数据、凭据写入 localStorage。
- 仅通过后端认证会话访问真实交易接口。
- 建议服务端对有副作用的操作增加 CSRF、防重放、幂等键、来源校验和审计记录。

### 10.4 可维护性

- 所有 API 方法集中在一个 API 区域。
- 所有 DOM 选择器集中或通过明确 ID 获取。
- 状态对象集中管理，不允许事件处理器内散落全局变量。
- 金额、价格、数量、百分比格式化方法统一。
- 交易类型、报价方式、委托状态映射集中定义。
- 每个操作函数采用“校验 → 确认 → 请求 → 刷新 → 反馈”的清晰结构。
- 注释重点说明业务规则，不写无价值的逐行注释。

## 13. 错误处理与异常提示

### 13.1 统一错误类别

- 网络不可达。
- 请求超时。
- HTTP 非 2xx。
- `Result.success === false`。
- `Result.msg` 业务错误。
- JSON 解析失败。
- 账户登录状态失效。
- 账户无对应期权权限。
- 委托价格超限。
- 委托数量超限。
- 可用数量不足。
- 委托状态已变化、已成交或已撤。
- 撤单单笔失败。
- 快捷交易部分完成。
- 快捷交易结果待核实。
- 后端逻辑阻断。

### 13.2 错误展示

- 优先显示后端返回的业务 `msg`。
- 对用户可理解的错误，说明下一步如何核查。
- 不显示完整 Cookie、SID、validatekey、内部请求头和账户敏感数据。
- 不将后端堆栈作为普通交易提示显示。
- 真实交易请求发生网络错误时，提示用户先刷新委托核对，禁止立即重复提交。

### 13.3 结果待核实场景

下单、撤单、分档单、清仓等请求发送后发生超时或连接中断时，不能简单显示“失败”。请求可能已被服务端或券商接收。

统一处理：

1. 将操作状态标记为“结果待核实”。
2. 禁止自动重复提交。
3. 引导刷新当日委托、可撤委托和持仓。
4. 通过真实返回的委托号、委托列表和持仓变化核对。
5. 只有在查明原请求未被受理后，才允许用户重新发起。

# 附录 B：本需求的最终硬性原则

**要实现的是一套完整连接现有真实后端的交易页面，而不是一个展示型 Demo。**

- Controller 当前开放的 15 项能力，一个都不能漏。
- 用户能在页面上找到每一项功能的明确入口。
- 数据必须来自真实 API。
- 交易结果必须从真实委托和持仓刷新核实。
- 不能把内部 Service 方法或已注释代码虚构成公开 API。
- 不能用前端模拟来掩盖后端缺陷。
- 不能暴露任何交易会话凭据。
- 单文件优先，原生技术栈优先，代码结构清晰优先。
- 源码发现的 P0 交易逻辑风险必须修复并通过验证后，才能将相应快捷交易功能标记为生产可用。
